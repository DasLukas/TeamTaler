# Security policy

## Supported versions

Security fixes are provided for the latest stable minor release. Operators should run a pinned release image and apply supported updates after creating a verified backup.

| Version | Supported |
| --- | --- |
| Latest stable release | Yes |
| Older releases | No |
| Development branches | No production support |

## Reporting a vulnerability

Do not disclose an unpatched vulnerability in a public issue, pull request, discussion, or chat.

Use the repository's private GitHub Security Advisory reporting flow. Include:

- Affected version or commit.
- The smallest reproducible scenario.
- Expected and observed behavior.
- Security impact and required privileges.
- Any suggested mitigation.

Maintainers will acknowledge a complete report within seven calendar days, validate the finding, coordinate a fix and release, and credit the reporter when requested. Please allow a reasonable remediation window before public disclosure.

## Security model

TeamTaler treats the following as security boundaries:

- Group isolation and object-level authorization.
- Global system-role isolation from every group role and membership.
- Versioned instance settings, encrypted write-only SMTP credentials, and tested SMTP revisions.
- Archived-only permanent-purge controls with optimistic concurrency, exact-name confirmation, transaction-scoped deletion guards, and minimal retained receipts.
- Stable permission-key enforcement for group configuration, membership management, role definitions, finance, catalog, booking activity, own-account payments, own booking creation, booking reversal, third-party booking, member-directory reads, and group-statistic reads.
- Credentialless temporary-guest identity, privacy-minimized booking data, history-preserving login claims, and tombstone-backed membership removal.
- Protected role administration and the invariant that every group retains an active assignment of its reserved group-administrator role.
- Authentication sessions, password reset, verified email changes, invitation links, public join links, verified registrations, and CSRF protection.
- Append-only financial corrections and auditable administrative changes.
- Server-enforced settlement availability and immutable period history.
- Image parsing and local file storage.
- Trusted reverse proxy headers and canonical origin validation.
- Backup archive validation and upgrade safety.

A person with unrestricted access to the host, container volume, or SQLite file can read or change application data. TeamTaler does not claim tamper resistance against a compromised host administrator. Operators are responsible for host hardening, TLS configuration, encrypted offsite backups, and access to deployment secrets.

`SYSTEM_ADMINISTRATOR` is a global database assignment keyed by stable credentialed user ID. It is deliberately separate from group roles: it grants the System workspace and system endpoints but no implicit membership, member directory, catalog, booking, finance, or group-audit access. Bootstrap assigns it only when creating the first account on an empty installation; existing installations require an explicit local CLI grant. HTTP exposes only a read-only administrator list. Grant and revoke remain host-local commands, the final active assignment cannot be revoked normally, and every protected request reloads the current assignment from SQLite. `Session.systemRoles` is a client-navigation hint and never an authorization source.

System-setting mutations require authentication, a current global role, CSRF and exact-origin validation, and strong `If-Match` optimistic concurrency. The service revalidates the role and resource version inside the serialized write transaction and emits a secret-free global audit event. Persisted settings override environment and code defaults but cannot override the host-only public URL, listener, trusted proxy CIDRs, storage paths, cryptographic key, container selection, or maximum request-body ceiling. Maintenance mode blocks ordinary mutations server-side with `503`; login, logout, safe reads, health probes, and system-administration recovery remain available.

The SMTP password is write-only. When stored as an override it is encrypted with a purpose-specific key derived from `TEAMTALER_EMAIL_TOKEN_KEY`; the key, plaintext, and ciphertext are never returned or logged. Every changed persisted SMTP revision is disabled until a rate-limited test message to the current system administrator succeeds for that exact revision. A later edit invalidates the test. TLS 1.2 or newer, certificate verification, and encrypted authentication remain mandatory. DNS is resolved immediately before dialing, connections use only the validated resolved address, and private or otherwise restricted targets are rejected unless the host explicitly trusts private runtime SMTP or the target exactly matches the immutable environment relay host and port. Email workers load current settings before a job and pause without consuming delivery attempts while SMTP or maintenance policy disables sending.

Web Push uses a separate `TEAMTALER_PUSH_STORAGE_KEY`. Purpose-separated HKDF output protects the stored VAPID secret and AES-256-GCM browser-subscription envelopes; only a SHA-256 endpoint hash is retained for uniqueness and neither endpoints nor client keys are returned by list APIs or written to logs. Subscription endpoints must be credential-free HTTPS URLs. Registration and delivery reject loopback, private, link-local, reserved, and otherwise non-public destinations, disable redirects, and connect only to the address resolved and validated for that attempt to limit SSRF and DNS rebinding. A shared browser subscription is atomically reassigned to the currently authenticated account, each account is limited to ten active devices, and a VAPID rotation invalidates the prior key identifier so clients re-register rather than silently using stale credentials. Client reconciliation binds the local device marker to the account that granted consent, refuses silent reuse after an account switch, and replaces unknown prior browser subscriptions only after a new explicit opt-in.

External notification delivery is derived inside the originating domain transaction from three fail-closed gates: the system channel must be active, the group must allow the event, and the member must enable that channel for that event. Email and push are independent and may both be selected. The authenticated in-app record remains canonical. Push payloads contain only the group name, generic event type, notification identifier, and protected application route; member names, product labels, monetary amounts, and settlement dates never leave the server in a push payload. Expired push work is discarded, `404` and `410` revoke subscriptions, `429` honors a bounded retry delay, and all other temporary failures use leased bounded backoff without exposing provider responses.

The effective media-upload limit applies to product images, group logos, and avatars. It is constrained to 256 KiB through 25 MiB, must fit beneath `TEAMTALER_MAX_REQUEST_BYTES` after multipart reserve, and does not weaken the 4096-pixel, 8-megapixel, or 10-MiB normalized-PNG limits. The server rejects oversized bodies with `413` before expensive decoding. Persisted setting values and UI validation do not replace the server-side request ceiling.

Authorization is additive: a membership's effective permissions are the union of grants in all assigned roles. There are no direct member exceptions and no deny grants. `VOID_ANY_BOOKING` implies `VOID_OWN_BOOKING` and `VIEW_ALL_BOOKING_ACTIVITY`; `MEMBER_MANAGEMENT` and `BOOK_FOR_OTHERS` imply the hidden compatibility read `VIEW_MEMBER_DIRECTORY`. Clients must use the server-provided effective grants and capabilities instead of recreating implication logic from role names. Group, category, and product scope shapes are tenant-bound in storage, but v1 accepts only group-wide grants. Mutation requests containing category or product scopes are rejected until resource-specific enforcement is implemented.

`CREATE_OWN_BOOKING`, `BOOK_FOR_OTHERS`, and `BOOK_FOR_GUESTS` authorize independent target classes. Self-booking can charge only the authenticated membership. Booking for others can charge only credentialed foreign memberships, follows the group's transaction-bound reason policy, and implies `VIEW_MEMBER_DIRECTORY`. Booking for guests can charge existing or newly created credentialless memberships and grants no directory access. A mixed batch must satisfy every permission represented by its targets. It revalidates current credentials, tenant ownership, active state, display names, current reason policy, product version, price, and open period before inserting any identity or accounting row. Guest identities, memberships, bookings, paired ledger entries, notifications, audit records, and the request-hash-bound idempotency result commit together, preventing partial batches, cross-group substitution, and duplicate guests on retry. Existing IDs and new names share a maximum of 100. Active temporary-guest names are case-insensitively unique; a `409` may disclose only the conflicting membership ID to an authorized guest booker so reuse remains explicit and never becomes an implicit merge.

Payment creation validates the selected group-owned method and the applicable self-service or finance-managed reason rule inside the same serialized write transaction as the immutable payment, ledger, allocation, audit, notification, and idempotency rows. Administrator-supplied labels are bounded plain text and never become authorization identifiers. Historical payments retain a method-label snapshot, so later option edits cannot rewrite financial history. The operational transaction-settings endpoint requires an active membership and exposes no administrator, role, directory, balance, or tenant-external data.

`settlementsEnabled` controls whether a group may close its technical open accounting period; it never changes authorization, ledger scope, or financial history. Period close rechecks both `FINANCE_MANAGEMENT` and the current setting inside the same serialized write transaction, so a stale or modified client cannot close a period after settlements have been disabled. The server returns a conflict and leaves the open period, ledger, statements, notifications, and successor-period state unchanged. Disabling or re-enabling settlements does not write a financial boundary: consolidated balances continue to use the complete ledger, the same open period receives new activity, and every existing closed-period snapshot remains immutable. Hiding current-period controls and conditionally showing history are presentation decisions only.

Local group-logo, profile-image, and product-image crop previews use browser-owned `blob:` URLs and never leave the device before the explicit save action. The content security policy permits `blob:` only in `img-src`; scripts, objects, connections, and navigation do not inherit that allowance. Uploaded PNG crops still pass through the complete server-side image validation and normalization pipeline.

A temporary guest remains a normal membership backed by a required user reference, but that user row has both email and password hash null under a database constraint. Authentication requires real credentials, so the identity cannot log in or receive a session. Synthetic addresses and placeholder passwords are forbidden. Credentialless temporary guests are the sole active-membership exception to the minimum-role rule and deliberately have no grants. Roles may be prepared only through an open claim invitation and are applied exactly when credentials are established. Every login-enabled active membership and pending invitation retains at least one explicit role. Notification delivery may retain an in-app event for the stable membership, but it never queues email while the address is null. Period statements preserve a nullable close-time email without weakening ledger or statement immutability.

`VIEW_MEMBER_DIRECTORY` protects membership email, role, and effective-grant data. It remains a hidden compatibility read so upgraded roles and `BOOK_FOR_OTHERS` do not acquire mutation rights. Only `MEMBER_MANAGEMENT` exposes archived membership lifecycle data. `VIEW_GROUP_STATISTICS` protects the dashboard's signed complete-ledger group outstanding amount; without it the field is omitted. `/booking-context` is a separate minimization boundary: it returns the actor's own balance and only membership ID, display name, optional avatar, and derived guest status for allowed targets. Booking activity carries only server-resolved actor and target display names, lifecycle states, and optional current protected avatar URLs for bookings already visible to the caller, so it does not need to fetch or widen access to the protected directory.

The reserved `GROUP_ADMINISTRATOR` role has the fixed name `Group administrator`, cannot be deleted, and cannot lose its direct `GROUP_ADMINISTRATION`, `MEMBER_MANAGEMENT`, or `ROLE_MANAGEMENT` grants. At least one active membership must retain an assignment of that exact role; a custom role containing `GROUP_ADMINISTRATION` does not satisfy the invariant. `MEMBER`, `FINANCE_MANAGER`, and `CATALOG_MANAGER` are editable starter roles with no special security status and may not be used as a default while granting either administration permission. Creating or modifying role definitions requires `ROLE_MANAGEMENT`. Assigning ordinary existing roles requires `MEMBER_MANAGEMENT`; assigning or removing the reserved role or any role containing `GROUP_ADMINISTRATION` additionally requires `GROUP_ADMINISTRATION`.

The group default role is a `MEMBER_MANAGEMENT`-owned convenience default for future invitations, not an implicit permanent assignment. It is tenant-bound by foreign key, cannot be deleted while selected, and cannot contain `GROUP_ADMINISTRATION` or `MEMBER_MANAGEMENT`. The same restriction is rechecked when settings or grants change, preventing CSV fallback from silently becoming an administrative privilege-escalation path. Other group-setting fields require `GROUP_ADMINISTRATION`; mixed updates require both permissions.

Individual member invitations remain usable without SMTP: creation stores only the token hash and returns the fragment URL once for manual delivery. Renewal always rotates the token and seven-day expiry, invalidates every older link, and returns the replacement URL once. The transaction queues an encrypted email envelope only when SMTP is active for that request, so an invitation created before SMTP setup can later be renewed, displayed, and delivered automatically without ever making a stored plaintext token recoverable.

Cross-group invitations for one normalized mailbox converge on one global account without merging tenant authorization. New invitations for an existing account store its stable user ID. When the first of several previously unbound invitations creates an account, the same serialized transaction binds every other open invitation for that mailbox to the new user ID. Each invitation still creates or reactivates only its own group membership and applies only its own explicit roles. The browser echoes the account state from its token-specific preview; acceptance compares that state inside the write transaction before hashing or verifying the submitted password. A concurrent first acceptance therefore makes every stale new-account form fail with a typed conflict without consuming its token. The client reloads the preview, clears password fields, and requests the current account password. Stable binding also prevents a later email-address change or address reuse from redirecting an already issued invitation to another account.

Global group creation never makes the acting system administrator a member implicitly. An existing initial-administrator account receives only the protected group-administrator role in a new active group. A previously unknown email address produces a non-usable `PROVISIONING` group and a protected first-administrator invitation regardless of SMTP availability; its one-time fragment URL is returned only in the immediate create response for manual sharing. Acceptance activates the group and establishes its first membership atomically. Until then, ordinary group routes cannot resolve the tenant. Replacing that invitation requires a live system-administrator assignment, CSRF and origin validation, the current group ETag, and continued `PROVISIONING` state. The serialized transaction revokes every open predecessor, cancels its unsent or retryable delivery work, stores only the new token hash, optionally adds its encrypted outbox envelope when SMTP is active, preserves the protected administrator assignment, advances the version, and returns the replacement link once, so a stale request or old link cannot race the replacement.

Archiving requires a live global system-administrator assignment and current group ETag. It immediately excludes the group from sessions, preferences, and ordinary group endpoints; disables public joining; invalidates open invitations and registrations; and cancels pending group mail jobs while preserving domain and accounting history for restoration. Restoring the group does not silently reactivate prior links, invitations, or registrations. The global public-join setting is an additional fail-closed gate: disabling it preserves group link records but makes every public link unusable until the global policy is enabled again.

Permanent purge accepts only an archived group and requires a live `SYSTEM_ADMINISTRATOR`, the current group ETag, and the exact current group name. A local non-interactive CLI purge requires `--confirm-name`; interactive use reads the exact name from the terminal. The transaction revalidates the administrator assignment and group state, narrows its deletion guard to one `PURGING` group, deletes all group-owned business, authorization, notification, idempotency, and group-audit rows, validates foreign keys, and appends only a global receipt containing the group identity, actor, time, and deletion counts. Shared global users and avatars remain.

Managed media deletion is asynchronous and idempotent. A process-wide content-hash lease coordinates publication, database attachment, reference checks, and removal so a concurrent upload cannot lose its newly referenced file. A job remains retryable while any product, group, or account still references the hash and removes it only after a later reference-free check. SQLite secure deletion and a verified truncated WAL checkpoint remove purged pages from the active database files; a busy checkpoint is recorded durably and retried by the maintenance worker without turning an already committed purge into a false failure. Application-level purge cannot erase copies in archives, off-host backups, host/volume snapshots, storage-controller caches, or physical flash remanence. Operators must apply retention and media-destruction policy to those copies separately.

Long-term guests have no special security classification. They are credentialed accounts governed by ordinary, additive roles and may use any safe default role. New groups seed ordinary editable roles named `Mitglied`, `Finanzverwaltung`, `Katalogverwaltung`, and `Gast`; none carries a preset key, and neither their names nor deterministic seed identifiers participate in authorization or identity classification. Temporary-guest creation is authorized only by `BOOK_FOR_GUESTS`; there is no feature switch or role-name heuristic.

Member and temporary-guest archive, reactivation, and permanent-removal commands require `MEMBER_MANAGEMENT`, tenant ownership, and a second authorization check inside the serialized write transaction. Archiving a membership with any role containing `GROUP_ADMINISTRATION`, or reactivating it with such a role, additionally requires `GROUP_ADMINISTRATION`. Archiving removes effective access and booking eligibility but permits finance-authorized settlement. Reactivating a credentialed member requires at least one ordinary role; a temporary guest remains roleless and may be renamed only after active-name uniqueness is rechecked. The last reserved group administrator cannot be archived. Permanent removal accepts only an archived, non-deleted membership and rechecks its exact zero receivable balance in the same transaction as the tombstone conversion. Deleted state is immutable, cannot receive roles or claim invitations, and is excluded from member and booking targets. A later reversal may create a new balance, but the deleted account then appears only in finance and accepts only a debt-reducing payment. The historical name and stable membership remain; prior email and avatar do not appear in current projections.

Temporary-guest rename and claim creation require `MEMBER_MANAGEMENT`. A claim targets only an active credentialless guest, requires at least one regular role, and permits at most one open invitation. Member managers may select ordinary roles; administrator-capable roles additionally require `GROUP_ADMINISTRATION`. Acceptance consumes the token once, preserves the membership and every accounting reference, attaches credentials or an authenticated existing identity, rejects a conflicting group membership, clears the temporary name key, and assigns exactly the invitation's roles.

One reusable public join link may be enabled per group only by `MEMBER_MANAGEMENT` and only while complete TLS-secured SMTP delivery and authenticated token encryption are configured. Its random secret is hashed for lookup and separately encrypted for member-manager recovery; API request paths and server logs never contain it because browsers keep it in the URL fragment. Finite lifetimes range from one hour to 365 days. Unlimited links are an explicit member-manager choice and can be rotated or disabled immediately. Both operations invalidate the older URL and QR code plus every pending verification proof in the same transaction.

Existing accounts must authenticate before a public join. New accounts receive a one-hour, single-use mailbox proof through the leased encrypted outbox; no membership is created before successful verification. Start and resend responses do not reveal whether an email address already belongs to an account or registration. Acceptance assigns the group's current safe default role rather than any role encoded by the link or client. Archived, non-deleted memberships are reactivated only after their former role set is replaced by that default, preventing retained privilege from an earlier membership. A permanently removed person joins through a new membership ID instead of reconnecting the tombstone.

Password-reset requests are account-enumeration resistant: a syntactically valid request receives the same empty `202` response whether the normalized address belongs to an eligible account or to no account. Password-reset and email-change tokens contain 256 bits of randomness, expire after one hour, are stored as SHA-256 hashes for lookup, and are consumed once. Plaintext exists at rest only as AES-256-GCM ciphertext in a leased email outbox until the relay accepts or the job is cancelled. Public browser URLs carry these secrets only in fragments, and clients submit them in JSON bodies; paths, query strings, API responses, logs, audit metadata, and safe outbox errors never contain them.

An authenticated password or email-change request requires the current password and CSRF protection. A new email address is normalized and checked against the database's case-insensitive uniqueness boundary, but the accepted start response does not reveal whether another account already uses it. The current address remains authoritative until mailbox confirmation succeeds. Password changes, password-reset confirmation, and email-change confirmation revoke every session for the affected user, including the session that initiated an authenticated change. Email confirmation mutates the existing user row instead of replacing the identity, preserving membership, financial, statement, and audit references. Consumed, cancelled, expired, or superseded tokens cannot be replayed.

When SMTP or authenticated token encryption is unavailable, public authentication capabilities report password reset and email change as unavailable, and both email-start commands fail closed with `503`. Hiding their controls is a usability measure only. Display-name updates and authenticated password changes do not depend on SMTP, while confirmation of an already delivered proof remains governed by its persisted expiry and one-time state.

Role and assignment mutations use strong version ETags. Services reload effective permissions and enforce the last-administrator invariant within the same serialized SQLite write transaction as the mutation, preventing stale sessions and concurrent demotions from creating a lockout. Permission results are not cached across requests. Frontend route guards and hidden controls are usability measures only and are never authorization boundaries.

Account-level group preferences are convenience navigation state, not authorization. The server accepts a fixed-default or last-used group identifier only when the authenticated user currently owns an active, non-deleted membership in that group. Session resolution rechecks the current group list and ignores stale references, so archived, deleted, or foreign groups cannot restore access.

## Operational guidance

- Expose TeamTaler only through HTTPS in production.
- Configure the narrowest possible trusted proxy CIDRs.
- Never place the SQLite database on NFS or SMB.
- Keep the data volume, backups, and reverse proxy credentials private.
- Run one TeamTaler application replica per database.
- Back up before every upgrade and test restores regularly.
- Grant system administration only to named credentialed accounts through the local CLI, keep at least two assignments where operationally appropriate, and review the global system audit.
- Review deletion-impact counts and a verified backup before group purge, then remove retained backup/snapshot copies separately when policy requires true data destruction.
- Review role assignments after migration `0017`; legacy category-specific grants are intentionally removed and must not be replaced with broader group-wide grants without an explicit access review.
- Before migration `0021`, verify a backup and update strict API consumers for nullable membership/statement email and the `isTemporaryGuest` field. The migration grants the two new read permissions to every existing role solely to preserve prior access and grants `BOOK_FOR_GUESTS` only to existing administrator roles; review and narrow those grants deliberately after rollout if needed.
- Before migration `0023`, verify a backup and deploy the matching API and SPA together. Permanent removal is intentionally irreversible at the membership-lifecycle level even though financial and audit history remains available through the tombstone.
- Migration `0026` grants `MEMBER_MANAGEMENT` once to every existing role with a direct group-scoped `GROUP_ADMINISTRATION` grant. Existing direct `VIEW_MEMBER_DIRECTORY` reads remain unchanged and do not gain mutation access; review custom administration roles after upgrade if their responsibilities should now be narrowed.
- Treat `BOOK_FOR_GUESTS` as authority to create persistent accounting identities. Review audit events and revoke it from roles that do not need temporary-guest booking.
- Prefer finite public join-link lifetimes, rotate a link after broad or unintended distribution, and disable it as soon as open enrollment ends.
- Preserve `TEAMTALER_EMAIL_TOKEN_KEY` while an account-action email may still be pending. Rotating or losing the key makes its encrypted proof undeliverable and invalidates a persisted SMTP password; it does not expose either plaintext.
- Preserve `TEAMTALER_PUSH_STORAGE_KEY` with database backups. Losing it makes stored browser subscriptions and a persisted VAPID override unusable; rotating the VAPID identity intentionally requires device re-registration.
- Do not log or share session cookies, invitation URLs, public join URLs, mailbox verification URLs, password reset material, or data archives.
